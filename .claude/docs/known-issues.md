# Known issues

- ISIN check digit: ISO 6166 Annex C is paywalled; enforced on the strength of SET's three worked examples and ANNA's naming.
- CUSIP: no official value for letters or `*@#`; the check is for all-digit CUSIPs only, the rest is format only.
- ISO 11649:2009 Annex A.3 prints `RF68 5390 0754 7034`, which fails clause 6.2; the valid pair is 18 (SIX IG, EPC069-12).
- OMG FIGI 1.0 lists 5 excluded prefixes in clause 2 and 7 (`GH`, `KY` too) in 6.1 and the regex.
- ISO/IEC 13239 is the reflected X.25 CRC; the EMVCo CRC (poly 1021, init FFFF, no reflection, no XOR) is fixed by the BCB payload `...6304AD38`.
- No official card-number vector for Luhn; no no-Luhn range in any reached publication.
- UPI (ISO 4914), Valor, Mastercard, Mir ranges, SBP and NPCI UPI documents: unreachable or unconfirmed (FINANCE.md).
- The Internet Archive was offline mid-research (2026-11-20); WebFetch cannot reach web.archive.org, curl can (allowed domain).
- Mastercard and Visa developer test-card pages are script-rendered: curl returns no numbers.
- Discover's IIN Range Summary prints the `a`/`b` footnote markers as superscripts above each row in text extraction;
  the marker belongs to the row below it (checked with `pdftotext -bbox-layout`). 3337-3349 is JCB. The unmarked rows
  are shared by Discover, Diners Club International and PULSE and name no single scheme, so `IinRanges` omits them.
- `PaymentCardNumber::masked()` uses `*` for hidden digits, keeps `min(6, length - 5)` leading and 4 trailing digits.
- `IinRanges` takes its table in the constructor (`IinRanges::default()` is the real one) so tests can use a synthetic
  table with a co-badged range; the real table has no overlaps.
- EMVCo QRCPS 1.1 is reached only through a third-party copy (emvco.com 404, no archive copy); HKMA and BCB quote the same tables. The 512-character payload limit is a "should" there and appears in neither HKMA nor BCB.
- EMVCo lengths count characters, not bytes: `Internal\EmvcoTlv` splits the payload with `preg_split('//u')` before slicing.
- `additionalData()` returns `list<DataObject>` since 1.0 (the 0.x keyed array turned `"10"` into an int); `additionalDataField()` gives the last value of a sub-ID.
- `Decimal` normalizes `10.50` to `10.5`; the written form stays in `get('54')`. A trailing mark (`98.`) is valid in EMVCo and is trimmed before parsing.
- BCB sets the postal code (ID 61) up to 99 characters where EMVCo and HKMA say 10: root value maxima are not enforced.
- String-format objects (sub-fields of 26-51, 62 sub-IDs 12-99, templates 64-99) accept UTF-8 and their lengths count characters; a decoder that counts bytes reads such a payload differently. That differential is spec-mandated (EMV QRCPS 4.4.1.1, 4.5.3); N/ans objects are limited to printable ASCII so they cannot show it.
- `masked()` hides IDs 02-51, 80-99, 62-02, 62-04, 62-06, 62-10, 62-50..99 and the CRC (`6304****`), and sets 62-08 and 64-03..99 to `***` (64-00 stays); the masked string is no valid payload. A 62 that is not TLV is masked whole.
- Annex B.7 of the EMVCo document has line breaks inside values in its printed text; use the hexadecimal representation printed under it.
- The GUI (sub-ID 00) is accepted anywhere in its template (EMV QRCPS 4.6.1); `MerchantPresentedQrBuilder` writes it first.
- DuitNow uses payload format indicator `02` and Thai QR makes ID 52 and 60 optional; the generic `MerchantPresentedQr` refuses both. `ProfilePayload` runs `Internal\EmvcoMerchantPresented::validate()` without the length bound on a modified copy (indicator 01, placeholders `0000` / `NA`, CRC recomputed) so no structural logic is duplicated; the bound is checked on the original, and the accessors and `masked()` answer from the original objects so no placeholder shows.
- The BCB's own BR Code example (manual 2.0.1, 2.2) has the txid `RP12345678-2019`; the Pix manual (2.6.2) says letters and digits only. `PixBrCode` does not enforce the charset.
- Pix dynamic and composite codes: value and txid in the QR are ignored by the payer (Pix manual 2.7); `txid()` returns null for `***`.
- PayNet's DuitNow pages are flagged "no longer updated" (V1.5); a newer PayNet docs site exists and was not read. Its four examples have valid CRCs.
- The Thai guideline prints no full payload; PromptPay tests are synthetic. Thai tag 29 AID `...114` is for customer-presented QR and is refused.
- bi.go.id drops curl connections; files there were read through WebFetch (binary saved by the harness). A browser-like User-Agent was not used.
- `Internal\ProfileRule::atMost` replaces min/max pairs: every present data object has at least one character, so the minimum 1 is implied.
- `Internal\EmvcoMerchantPresented` is the stateless generic validation (`validate($payload, bounded)`) and field derivation; `MerchantPresentedQr` calls it bounded, `ProfilePayload` unbounded on its modified copy (the 7089 bound runs on the original payload only).
- Single-value accessors of the profiles (`pixKey()`, `paymentUrl()`, `recurrenceUrl()`, `proxyType()`, `proxy()`) throw `AmbiguousPaymentQrFieldException` (a `DomainException`; the message names the profile, the field and the reason, never a value) when the payload carries several distinct values; their list accessors (`pixKeys()`, `paymentUrls()`, `recurrenceUrls()`, `proxyTypes()`, `proxyOf()`) never throw. `PixBrCode::additionalInfo()` and `withdrawalProvider()` throw when several Pix templates do not all carry the same value and have no list accessor.
- KHQR: the NBC specification only reserves tags 29/30 for Bakong and leaves their content to the operator; the Bakong account ID (`name@bank`) in sub-tag 00 is not an AID/UUID/reverse domain as the spec's GUI rule asks, so the GUI form is not checked. `KhqrCode` requires country `KH` (derived from the Prakas scope plus "Put KH ... if the merchant transacts in Cambodia"); without it every EMVCo payload with tag 29/30 (Thai QR, EMVCo Annex B.7) parsed as KHQR. A Cambodian code that also carries a PromptPay template is ambiguous in the factory.
- KHQR sources are Internet Archive `id_` copies: bakong.nbc.gov.kh answers 403 to curl; the Prakas appendix is a scanned PDF (no text layer) read as page images. The Content Guideline wraps payloads across lines; the strings in `KhqrCodeTest` are the joined forms whose CRC verifies.
- JPQR: the Payments Japan MPM guideline 2.0 prints only the template layout (`xx680019jp.or.paymentsjapan0113...`), no full payload; JPQR test payloads are synthetic. GUI matching is case-insensitive by inference (not stated).
- Pix key types: decoded from the DICT API 2.13.0 regexes (CNPJ is alphanumeric since 2026: `[A-Z0-9]{12}[0-9]{2}`); a key matching none gives `pixKeyType() === null` and is never refused. The DICT API GitHub repo `bacen/pix-dict-api` is obsolete; the current spec is the BCB HTML page.
- Not built and why: SGQR not reached (MAS/IMDA publications reached carry no data-object rule); QRIS doc only on written request (PADG 21/18 art. 5); VietQR base TCCS 03:2018 not reachable (Decision 2525 is customer-presented); HK FPS not reached (HKICL/HKMA publications reached carry no FPS template); Bharat QR spec 4.0 only to member banks.
- JPQR is the only profile with a byte bound: Payments Japan caps the payload at 512 bytes ("512byte を上限とする"), checked on the raw UTF-8 string before parsing; the generic 7089-character bound still applies elsewhere.
- `ProfilePayload::templateFields($id)` is the one reader of root-template sub-fields (KHQR/JPQR/DuitNow template 64); sub-IDs 10-99 come back as integer keys (PHP array-key conversion).
- SIX IG QR-bill 2.3 Annex A example 4 prints `RF720191230100405JSH0438`, which fails ISO 11649 (correct pair 24); `QrBill` refuses it, a test pins it. ISO 11649's own A.3 `RF68` example is the same kind of slip.
- Rulings: EPC refuses a separator after the last populated element (the source over the plan); the QR-bill counts every separator as an element boundary (a final LF is an empty element within the 34).
- EPC 331 bytes: the constructor bounds bytes, except text that fits one ISO 8859 set of section 2.1 (331 characters), so a transcoded `fromBytes()` payload still parses; `Internal\Iso8859` checks the sets with PCRE classes generated from the Unicode 8859-N.TXT tables (no extension), so validity does not depend on the host.
- GOST treasury accounts (`03...` at treasury BICs `00...`) fail the Order 515 key; they are outside the order's scope and accepted (`RussianAccountKey::isInScope`: first digit 1-9).
- GOST R 56042 text is only reachable via the stroyinf.ru mirror; it misprints `PayeeINN` as `PayeelNN` and Table 3 has Cyrillic letters in `PayerAddress`. Sberbank's PDF copy fails TLS verification in the sandbox.
- Bank of Russia key: the rule is Order 515 (1997), read on pravo.ppt.ru; not on cbr.ru. ConsultantPlus `cons_doc_LAW_16870` is Instruction 26-U, not 515. With BIC `049805000` the KO number `000` makes key 3 valid too (either-number rule).
- NSPK keeps the SBP link layout in its closed OPKTs standards portal; NPCI's UPI linking spec is member-only (OC 18 quotes `pa`/`pn` M, `tr` up to 35). Both classes are format only beyond that; test links are synthetic.
- Infection under coverage marks a test risky when `ProfileRule`/`EmvcoTlv` run without `#[UsesClass]`; plain `make test` does not show it.
- Payment payload classes keep their derived state in plain private properties (no defaults, except the nullable ones Rector's `RestoreDefaultNullToNullableTypePropertyRector` forces to `= null`). `readonly` is not possible: the state is set in `parse()`, which the vo-base constructor calls, and PHPStan reports `property.readOnlyAssignNotInConstructor`/`property.uninitializedReadonly` (no config change allowed). vo-base `^1.3` makes `serialize()` hold only `value` and re-runs `parse()` on `unserialize()`; other keys are ignored (0.1.0's own `Internal\ReparsesOnUnserialize` refused them, removed in 0.2.0). `__unserialize()` is public and refuses (`LogicException`) on a built object: otherwise a direct call would re-run `parse()` and overwrite the derived state.
- `PaymentQrFactory` marker detection (final review CR-002): it TLV-parses the root once and marks Pix (GUI in 26-51), JPQR (GUI in 26-51), DuitNow (AID in 26), PromptPay (AID 29/30), KHQR (template 29/30 with country KH); only marked profiles are constructed. An accepting profile wins over an identified one that refuses; when all identified refuse, `MerchantPresentedQr::tryFrom()` is the fallback (O3), else the first refusal. The fallback hides a mis-identification, so the mutation tests need payloads the generic class refuses too (no ID 52) and assert the `MerchantPresentedQr ` message prefix.
- `MerchantAccount` used to compare its value with `[00 GUI, ...subFields]` in that order, so a template whose GUI is not the first sub-field (allowed, EMV QRCPS 4.6.1) made `merchantAccounts()` throw; since accounts are cached in `parse()` it would have refused the payload. It now takes the first sub-ID 00 wherever it is.
- `Internal\PayloadBound::ensure()` is the shared 7089-character bound (EMVCo, profiles, GOST, SBP, UPI, factory pre-scan); `ensure()` lets non-UTF-8 text through below 4×7089 bytes, so GOST `fromBytes()` uses `ensureSingleByte()` (7089 bytes) before transcoding WIN1251/KOI8-R.
- `PaymentQrFactory` returns the `PaymentPayload` interface since 1.0 (was an 11-class native union, a BC trap for every new profile).
- `SecurityIdentifierFactory` leaves `Valor` out (1.0 ruling S9): its sourceless 1-9 alphanumeric shape made every MIC, WKN, CFI, SEDOL and CUSIP ambiguous. Remaining overlaps: ISIN/FIGI, CFI/WKN.
- The php-cs-fixer template joins multi-line call arguments onto one line: wrap long calls with local variables or helpers, not with line breaks.
- PHPUnit `requireCoverageMetadata` is off, but Infection runs strict coverage: a test that executes `PayloadBound` (any EMVCo, GOST, SBP, UPI parse) needs `#[UsesClass(PayloadBound::class)]`. Check with `XDEBUG_MODE=coverage vendor/bin/phpunit --strict-coverage --coverage-xml=<dir>`.
- Revisit (final review CR-022): some industry references claim certain China UnionPay PANs carry no Luhn digit; no UnionPay publication was found, so Luhn stays mandatory. If one confirms it, a mandatory Luhn would refuse valid cards.
- Infection shares `sys_get_temp_dir()/infection` with other checkouts running at the same time ("JUnit file could not be found"); run it with `TMPDIR=<own dir>`. `--filter=src/A.php,src/B.php` runs only the mutants of the changed files.
- Coverage counts only `#[CoversClass]`: a mutant in a helper reached through `#[UsesClass]` only (e.g. `Internal\Mask` from a profile test) escapes even when the assertion would catch it; test the helper in the class that covers it (`TextHelpersTest` covers `Mask`, `ProfilePayloadTest` covers `EmvcoMask`). Every test that runs `EmvcoMask` needs `#[UsesClass(Mask::class)]` since names are masked.
- `Mask::name()` uses `preg_match('/./su')` without `^`: with a caret the PregMatchRemoveCaret mutant is equivalent. No mbstring (only suggested).
- Enum backed values are frozen (`BackedValuesTest`); `CardScheme::UnionPay` stays `unionpay` (lowercase one word), since an enum cannot accept an old value as an alias and 0.x rows stored through `enumType` must keep loading.
- `QueryString::filled()` reads `''` as absent only when it is the only occurrence; `am=&am=10` throws `AmbiguousPaymentQrFieldException`, as `single()` does. Review fix10 CR-009 asked to read it as `10`; declined by the controller (security: parser differential, a first-wins parser reads no amount there). Do not "fix" it.
- `JpqrCode::postalCode(): string` overrides the `ExposesRootFields` trait method (`?string`): a class method wins over a trait method, and the narrower return type is covariant with `EmvcoPayload`. Its `?? throw LogicException` arm is unreachable (61 is mandatory in parse), so the Infection `Throw_` mutant there is equivalent, like those of `storeId()` and `alternateMerchantName()`.
- GOST Annex V (table В.1) on the stroyinf mirror prints `Docldx`, `PayerldType`, `PayerldNum`, `Counterld`, `Quittld`, `Ruleld`, `Execld` with a lowercase L; the code uses the capital-I spelling of the Annex D text and the repo.
- SBP `masked()` rebuilds the query from parsed pairs (`QueryString::rewritten()`), fail-closed: only `type`/`bank`/`sum`/`cur`/`crc` in a code shape stay; other pairs become `***=***`, `***=` or `***` (names hidden too, fix11 R11-01).
- GOST `CounterId`, `ExecId`, `RuleId` are masked with keep-ends (fix11 R-01): `ExecId` is searchable in the FSSP database by debtor, `RuleId` is one person's traffic fine. `Contract` is free-form, so `***` (S-03). Any alias outside table В.1 is `***` (R11-03): `Gost56042Payload::VISIBLE` is table В.1 minus the masked aliases; everything else defaults to `***`.
- QR-bill billing information: `masked()` keeps only Swico S1 (`//S1` + ascending known tags in their forms) and stars its free-text tags 10 and 20; anything else, `//anna@x.com` included, is `***`. Parse does not check the syntax (0.x values keep loading).
- Masking residual (fix11 round 4): a phone number written as an amount or a numeric code of the same length (EMVCo 54/56, GOST `Sum`/`AddAmount`/`OKTMO`/`CounterVal`, SBP `sum`, UPI `am`/`mam`) is indistinguishable and stays visible; `MaskedLeakTest` skips exactly those pairs.
- EMVCo root shapes live in `EmvcoMask::ROOT_SHAPES`; numeric-string IDs (`'52'`) become integer array keys, hence `array<array-key, ...>`. The 54/56/57 length bounds (13/13/5) are the table 3.6 "var. up to" maxima used for masking only; parse does not enforce them.
- GOST masking shapes (`Gost56042Payload::SHAPES`) are masking shapes, not validation: Annex V leaves formats to the unreached УФЭБС album.
